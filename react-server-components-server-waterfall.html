React Server Components did not kill the waterfall, they moved it to the server

July 23, 20265 min readBy Harman Kamboj
ReactNext.jsRSCPerformance

The first time I shipped a page built almost entirely from React Server Components, it was slower than the client version it replaced. Not by a rounding error. By close to a second on first load, warm cache, fast box. I had done what the migration guide asked. The fetching lived in async server components, no useEffect was chasing an endpoint, and the network tab looked clean. It was still slow, and it took me an embarrassingly long afternoon to see why. The React Server Components waterfall had not gone away. It had moved to the server, where devtools no longer showed it to me.

That is the part nobody puts in the migration notes. Moving a fetch to the server changes where it runs. It does nothing about whether it blocks the fetch that comes after it.

What the waterfall used to look like

On the client the pattern was at least honest, because you could watch it happen. A component mounts, fires a request in an effect, waits, sets state, and only then does the child mount and fire its own request. Open the network panel and there is the staircase. Request one finishes at 200ms, request two starts at 210ms and finishes at 450ms, and the thing the user actually came for shows up at half a second even though neither call was slow by itself. We spent years learning to hoist those fetches up and colocate data with routes so the requests could leave together.

RSC promised to make a lot of that disappear, and it does remove the client roundtrip. What it quietly keeps is the shape of the dependency.

The same staircase, now invisible

Here is the version that got me. A server component awaits the user, then renders a child server component that awaits that user's projects, which renders a grandchild that awaits the activity for those projects. Each await runs on the server, each one is fast, and each one still waits for the one above it to finish before it even starts. Three fetches that could have gone out at the same moment are standing in a line instead.

What makes this nastier than the client version is not the raw latency. It is that you cannot see it. On the client the network panel was screaming the staircase at you. On the server the whole thing collapses into one slow response and a flame graph you have to go looking for. Nothing errors. Nothing warns. The page just takes 900ms to stream its first byte, and you shrug and decide that is the cost of server rendering.

I have watched sharp engineers stare at exactly this and conclude that RSC is slow. It is not. Their fetches are queued behind each other for no reason at all.

async and await is doing what you told it to

This is worth sitting with, because the fix drops out of it. await means stop here until this resolves. When you await the user in the parent and then render a child that awaits the projects, you have written, in plain code, "do not even begin loading projects until the user has come back." JavaScript is honouring that to the letter. The tree structure of your components has quietly become the execution order of your data, and most of the time that ordering is an accident of where you dropped the fetch, not a real dependency.

Real dependencies do exist. If you truly need the user's team id before you can ask for the team's projects, that await has earned its place. But most of the waterfalls I find are the other kind. The child needs nothing from the parent's fetch. It just happens to sit inside it in the JSX.

How I actually unwind it

The first thing I do is pull apart two questions that get tangled together. Does this fetch depend on data from another fetch, or does it only depend on a prop I could have passed down from higher up? Nearly every accidental waterfall is the second one.

For fetches that do not depend on each other, I start them together. Kick off the promises in the parent without awaiting them one at a time, then hand them down or resolve them side by side with Promise.all. The requests all leave at once, so your slowest call sets the floor instead of your sum. On the page that first embarrassed me, that single change took first load from around 900ms to a little over 300, because the three calls I had lined up were each roughly 250ms and now overlapped.

For fetches that genuinely are dependent, I stop trying to force them parallel and instead stop them from blocking the shell. Wrap the slow branch in Suspense, send the rest of the page straight away, and let the dependent part stream in when it lands. The user sees something at 150ms rather than a blank screen until the deepest fetch returns. Where you put that boundary changes what the user actually feels, which I got into in the piece on Suspense boundaries and layout shift, because a boundary in the wrong spot trades one problem for another.

The mental switch that made this click was to treat data fetching as its own graph, drawn on purpose, and to stop letting it fall out of the component tree by default. The tree is how you compose UI. It is a poor way to decide the order your network calls run in.

What I check before I trust a server page

When a server-rendered route feels sluggish, caching is not where I start. I look at the fetch dependency shape first. A quick way to surface it is to log a timestamp at the start and end of each fetch on one request, then read them back in order. If call B starts a few milliseconds after call A ends, and B never needed anything A returned, you have found free latency you get to delete. Do that before you cache anything, because caching a waterfall only gives you a fast waterfall, and the first uncached visitor still pays the whole bill. Most of my Next.js performance work starts here rather than at the CDN.

None of this is an argument against React Server Components. I like them and I would reach for them again tomorrow. It is an argument against believing the model fixed a problem it only relocated. The waterfall is a data-dependency problem, and data-dependency problems do not care which side of the network they run on. Draw the graph, run the independent things together, stream the rest behind a boundary, and the server page finally gets as fast as you expected it to be the first time. On a product like GatheredHere, where the data was the product, that difference is the whole experience.
