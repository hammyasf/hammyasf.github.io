MCP or a direct API call? When I skip the tool server

July 6, 20265 min readBy Harman Kamboj
AIAgentsMCPTooling

I have wired agents to tools a few different ways over the last couple of years, and the honest answer nobody wants at the start of a project is that the MCP vs direct API question is not a moral choice. It is a plumbing decision. Half the teams I talk to reach for an MCP server the moment they hear the word agent, then spend a week debugging a transport layer they never needed.

So let me lay out what the Model Context Protocol is good at, because it is good at real things, and then when I quietly skip it and just call the API.

What MCP actually buys you

MCP standardizes how an agent discovers and calls tools. You write a server once, and any MCP-aware client can use it without you hand-rolling a fresh integration each time. That pays off when you have many clients, or many tools, or when people outside your team will plug into the surface you expose. For a platform play it is the right shape, and the discovery story is genuinely nice once you have five agents and twenty tools sharing the same catalog.

The catch is that all of that generality has a price, and you pay it whether or not you actually need the generality.

When I skip MCP and call the API directly

If my agent talks to one or two services that I own, I skip the server and call the API straight from the tool function. No separate process, no transport to babysit, no schema handshake over the wire. The model gets a small set of typed functions, each one a thin wrapper over an HTTP call or a database query, and that is the whole thing.

Here is why I lean this way more often than the current hype suggests:

  • One less moving part. An MCP server is another process to run and deploy and watch. When it hangs, your agent hangs, and now you are debugging two systems instead of one.
  • Tighter schemas. When I own the tool function I shape the input and the output exactly for this agent. A generic MCP surface tends to hand the model everything, and that bloats the context window fast. I got into this in your MCP server is eating the context window. A hand-written tool returns the three fields the model needs, not the forty the API happens to send back.
  • Faster iteration. Changing a direct tool means editing a function. Changing an MCP tool means editing a function, restarting a server, and re-checking that the client picked up the new schema.
  • Error handling I control. I can catch the specific failure, retry against a budget, and give the model a clean message instead of a raw stack trace. That is much easier when the call lives inside my own code.

The test I actually use

Before I add an MCP server I ask one question: will this tool be reused by clients I do not own? If yes, MCP earns its place, because a standard interface is the entire point of it. If the answer is no, and early on it usually is, a direct call is less code and fewer ways to fail.

The second question is about count. One agent hitting a couple of internal services does not need a protocol sitting in front of it. A fleet of agents pulling from a growing library of tools across several teams does, because at that scale the standard saves you from writing the same glue over and over. Between those two worlds there is a real line, and most projects live well below it for a long time.

Where an MCP server is worth it

I do not want this to read as anti-MCP, because it is not. When I built product surfaces on top of on-chain data at Shiba Inu, the value of a shared, well-described interface was obvious the moment more than one thing needed to read the same data. That is the situation MCP is built for: many consumers, one contract, and a discovery mechanism so nobody has to memorize your endpoints. If you are shipping a tool platform other developers will build against, reaching for the protocol early is the correct call, not premature.

The mistake is adopting it for the future you imagine instead of the system you have. Teams stand up a server, wrap one internal API in it, and now every request takes an extra hop through a process that exists to solve a problem they will not have for months. You can always move a direct tool behind an MCP server later. Ripping out a protocol you leaned on too early is the expensive direction.

The part that matters either way

There is a subtler trap worth naming. Wrapping an API in MCP does not make that API ready for an agent. If the underlying endpoint returns a giant blob, paginates awkwardly, or fails in ways the model cannot read, the protocol passes all of that straight through. The work of making a tool good for an agent, meaning small inputs, small outputs, readable errors, and idempotent writes, is the same work no matter how the call is transported. I care far more about that than about which side of the MCP line I land on.

How I would start today

If I were beginning a new agent this week, I would write the tools as plain functions, get the loop working end to end, and feel where it actually hurts. Most projects never outgrow that setup. The ones that do, usually because tools need to be shared across teams or handed to outside developers, are exactly the cases where MCP stops being overhead and turns into leverage. You will know when you get there without guessing, because maintaining the same integration in three places gets loud in a hurry.

MCP is a strong answer to a specific question. Just make sure you are asking that question before you build for it. For more of how I think about this stuff, the AI and agents hub collects the rest.
