Streaming made my CLS worse: the Suspense boundary was in the wrong place

July 19, 20266 min readBy Harman Kamboj
ReactNext.jsCore Web VitalsPerformance

The pitch for streaming is easy to like. Stop blocking the whole page on your slowest query, send the shell immediately, let the slow parts arrive when they are ready. First paint gets faster, LCP drops, the demo looks great on a fast laptop. Then the field data comes back a week later and your layout shift score is worse than before you touched anything. If your Suspense boundary CLS numbers went up after you added streaming, the boundary itself is rarely the problem. Where you put it is.

I have shipped a fair amount of Next.js and React work where this exact tradeoff decided whether a page felt fast or felt broken, and I keep seeing teams optimise the wrong half of it. So here is how I think about it now.

What is actually moving

When a boundary resolves, React swaps your fallback out and drops the real content in its place. The browser reflows. If the skeleton was 180 pixels tall and the thing that arrives is 460, every element below it jumps down by 280 pixels. That jump is a layout shift, and the browser scores it by how much of the viewport moved and how far it travelled. Nobody clicked anything, nobody scrolled, the page just rearranged itself under the user's thumb.

The advice you will find everywhere is to make your skeleton the same size as the content it replaces. That is correct and it is also the part most teams cannot actually do.

Why matching skeleton heights falls apart

Matching works when the content has a known fixed size. An avatar, a price, a chart with a set aspect ratio. It stops working the moment the server decides how much comes back.

  • A list of results is however long the query says it is. Your skeleton renders five rows and the API sends nine.
  • Text wraps differently at every breakpoint. A skeleton you tuned on a 1440 pixel monitor can be sixty pixels off on a phone, and CLS is measured on the phone.
  • Content that appears conditionally, like a warning banner or an empty state, exists in one branch and not the other.
  • Fonts land at different times. Your skeleton uses the fallback metrics, the real text uses the web font, and the line count changes.

You can chase all of that. I have chased it. You end up with skeleton components that carry more layout logic than the components they stand in for, and they drift out of sync the first time someone edits the real one and forgets the fake one.

Position decides the damage, not height

Here is the thing that changed how I place boundaries. A layout shift only counts if it moves content that is currently visible. Everything below the fold contributes nothing, because it was never on screen to move.

So the same 280 pixel mismatch is either a disaster or completely free depending on where it sits. Put that boundary in a hero section and it drags the entire page down while the user is reading. Put it in a section three screens down, and the fallback resolves long before anyone scrolls to it. Same skeleton, same mismatch, one of them costs you the metric and the other one does not.

Which gives a rule I actually apply: stream the things below the fold, and block on the things above it. If a query is slow and its output has to be at the top of the page, streaming it is usually the wrong call. Waiting a little longer for a page that arrives whole beats a page that arrives fast and then rearranges itself. Users forgive a slightly slower load. They do not forgive tapping a button that moved.

How I place boundaries now

First question is whether the slow content needs to be above the fold at all. A lot of the time it got there because of a design decision nobody has revisited, and moving it down solves the performance problem and nothing else changes.

If it has to stay at the top and the query is slow, I fix the query rather than hide it behind a skeleton. Cache it, precompute it, split it so the part that renders first is cheap. Streaming is a way to reorder work, not a way to make slow work fast, which is roughly the argument I made in my notes on what actually makes a Next.js app fast.

Below the fold I stream freely and I stop agonising over exact skeleton dimensions. I still give the container a sensible min-height so the page does not collapse and then expand, but I am no longer trying to match pixel for pixel, because it does not pay for itself down there.

And I never use fallback={null}. That is a boundary with no reserved space at all, so whatever arrives pushes everything after it. It looks tidy in the code and it is the worst option for the metric.

Streaming is not your only source of shift

Worth checking before you blame Suspense. Content that renders differently after hydration will shift too. A date formatted in the user's locale, a nav bar that swaps once auth resolves, a client-only widget that renders nothing on the server. None of that shows up while you are developing on a fast machine with warm caches, and all of it lands in field data.

Re-render behaviour feeds into this as well, since a component that recalculates and resizes on every state change is doing small shifts continuously rather than one big one. I wrote separately about why React components re-render more than you think, and the debugging approach carries over.

Measure it where it happens

A Lighthouse run gives you one scripted load on a simulated connection with no scrolling and no interaction. Field CLS is collected across the whole page lifetime, including shifts that happen when a real person scrolls into a boundary that had not resolved yet. Those two numbers can disagree loudly, and the field one is what ranks.

The tools I reach for are the Chrome DevTools performance panel with layout shift regions turned on, which literally paints a box over what moved, and the web-vitals library built with attribution, which hands you the specific element responsible instead of a score. Once you know which element it is, the fix is usually obvious and usually takes ten minutes. Finding it is the whole job.

The short version

Streaming trades one problem for another. You get a faster first paint and you accept that parts of the page will arrive late and move things. That trade is good below the fold and bad above it, and no amount of skeleton tuning changes which side of the fold you are on. Decide where the boundary goes first, then worry about what the fallback looks like.
