Session keys and the frontend: the session ends before your UI notices

July 27, 20266 min readBy Harman Kamboj
Session keysAccount AbstractionWeb3Frontend

Every swap and bridge screen I have shipped collected the same complaint. Too many wallet popups. You click a thing, a modal slides in, you squint at a hex string, you approve, and then twenty seconds later you do it again. Session keys are the answer the ecosystem landed on, and they work: a temporary key with narrow permissions signs on the user's behalf so the app stops interrupting them. What almost nobody designs for is the ending. Your frontend is the last part of the system to learn that a session key stopped working.

I have not shipped a session-key flow at Shiba Inu scale, so take this as an opinion formed from the thing session keys replace. I built the swap frontends and the bridge UI where every action meant a signature, and I have spent enough time in that code to know exactly which assumption is about to bite people.

What a session key actually hands your frontend

The mechanics are simple enough. The app generates a keypair, the user authorizes it once against their smart account under constraints, and from then on the app signs locally and submits without a prompt. The constraints usually cover an expiry time, a spend cap, a list of contracts or function selectors it can touch, and sometimes a call count.

Notice what moved. Signing authority used to live in the wallet, which is a thing your app can query and which fires events when it changes. Now a slice of that authority lives in a temporary credential your app is holding, governed by rules enforced on-chain, in a contract your frontend is not subscribed to. You have taken over responsibility for state you have no reliable way to observe.

Why session keys break the frontend state model

Most dapp state machines have one boolean that means everything: connected. Wallet connected, therefore user can act. It is wrong now, and it was already getting wrong when EIP-7702 made a plain address able to carry code. With session keys the gap widens, because a connected wallet and a working session are two different facts and only one of them has an event listener.

A session can die in at least four ways, and your app sees none of them directly.

  • Time runs out. The validity window closes. This one is at least predictable if you stored the expiry, which plenty of implementations do not bother to surface.
  • The user revokes it. Maybe from their wallet's permission screen, maybe on a different device, maybe from a security tool. Your tab has no idea.
  • The budget is spent. The spend cap or the call count is exhausted, so validation now fails on a session your UI still considers healthy.
  • The account changed underneath you. The user upgraded their account, swapped a validator module, or re-delegated. The session key was attached to a configuration that no longer exists.

In every case the first signal your frontend gets is a failed user operation, and bundler rejections are famously unhelpful. A validation failure code does not tell you whether the session expired, got revoked, or ran out of allowance. So the user sees a generic red toast and reloads the page, which is the worst possible outcome for a feature whose entire purpose was to make the app feel calm.

The standardisation gap makes this worse

If session keys were one standard you could write one handler. They are not. What a session key is allowed to do, how it is stored, and how it gets revoked all vary by SDK. A revoke button in one wallet may not touch a session your app created through a different stack. You cannot assume the user's wallet and your session logic agree about what is currently permitted.

Practical consequence: never treat a wallet-side revoke as the whole revocation story. If the session key can be killed from your side too, build that path, and build the check that notices when someone else killed it.

What I would build instead of a connected boolean

Treat the session as a lease with a visible remaining balance, not a login. Concretely, the things I would insist on:

  • Store the full permission envelope, not just the key. Expiry, cap, spent so far, allowed targets. If you cannot render what the session is still permitted to do, you cannot warn the user before it fails.
  • Check permissions before you sign, not after the bundler rejects you. Cheap local checks against the stored envelope catch the common cases with zero latency.
  • Use a safety margin on expiry. A session with forty seconds left will pass a local timestamp check and still be past its validity window by the time it lands on-chain. I would refuse anything inside a minute or two of expiry and re-authorise instead.
  • Re-authorise proactively. Ask for a fresh session while the user is idle or between actions, not in the middle of the transaction they care about.
  • Reconcile on focus. When the tab wakes up, re-read the on-chain permission state before letting the user act. That is where a revoke from another device gets caught.

On storage, I would keep the session key as a non-extractable WebCrypto key in IndexedDB rather than a string in localStorage. Same convenience, but a script that gets into your page can use the key while the tab is open instead of walking away with it. Given that a stolen session key lets someone act without ever touching the main key, that difference is worth the extra hour of work.

The scope people get wrong

The temptation is to ask for a wide session once so you never have to ask again. Broad target lists, generous caps, long expiry. It tests beautifully and it is how a small bug becomes a large withdrawal.

There is a second cost that is easier to miss. Session keys usually ship alongside sponsored gas, and I have already written about how a paymaster is not actually free. Stack the two and the user stops feeling anything at all: no prompt, no fee, no friction. That is the goal right up until the moment small amounts start leaking and nobody notices because nothing ever asked. Somewhere in that flow the app still owes the user a running total of what it has spent on their behalf.

What I tell teams now

Design the ending first. Before you write the code that creates a session, write the screen that appears when the session is gone, and decide how you detect each of the four deaths above. Sessions are a UX feature whose hard part is failure, the same way an intent-based swap UI stops being about the happy path the moment a solver does not fill.

Get that right and session keys are the best onboarding improvement this ecosystem has produced in years. Get it wrong and you have built an app that occasionally, silently, stops working with no explanation. More of my notes on this stuff live in my Web3 writing.
