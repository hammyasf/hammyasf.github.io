Rollback netcode in the browser: determinism is the hard part

July 14, 20265 min readBy Harman Kamboj
Game devNetcodeMultiplayerDeterminism

Every few months rollback netcode goes around the game dev timelines again, usually right after someone posts a buttery clip of a fighting game holding up fine on a bad connection. Then the indie crowd, me included a few years back, decides the next little browser game needs rollback too. I want to save you a couple of weekends. Rollback netcode in the browser is not the hard part. Determinism is, and if you jump straight to the netcode you will build something that desyncs in ways you cannot reproduce.

Quick refresher, because the two common models get muddled. Lockstep waits. Every client sends its inputs for a frame, and nobody advances until all of them arrive, so the whole game stalls for the slowest player and feels awful the moment someone's ping climbs. Rollback fixes the feel by guessing. It predicts the remote player's input, keeps simulating, and when the real input lands a few frames later it rewinds, replays the missing frames, and corrects. Done well you never see it happen. Done on a shaky foundation it is one of the worst things you will ever try to debug.

Rollback netcode is not your first problem

Here is the bit the flashy demo skips. Rollback only works if your game is deterministic. The same starting state plus the same sequence of inputs has to produce the exact same result on every machine, every time, frame for frame. If it does not, the rewind-and-replay step rebuilds a slightly different world than the one your opponent is running, and the two games quietly drift apart. That drift is a desync, and desyncs from nondeterminism are the nastiest bugs I have chased, because they only appear between two specific machines after a specific run of events, and never when you are watching.

So the real work was never the rollback buffer or the input prediction. Those are a known pattern you can lift from any decent write-up. The work is building a game loop that spits out identical output from identical input, and the browser makes that harder than most places you could be writing a game. It is the same trap I keep pointing at with WebGPU not fixing a slow browser game. The shiny layer is not where your problem lives.

Where JavaScript makes determinism harder

If I sit down to make a browser game reproducible, these are the places it tends to leak.

  • Floating point. JavaScript numbers are doubles, and functions like Math.sin, Math.sqrt and friends are not guaranteed to return the same last bit across engines or platforms. One player on an old phone and one on a laptop can diverge on the third decimal, and three seconds later they are in different fights. Fixed point math or a shared deterministic math library is the usual escape.
  • Iteration order. If you resolve collisions or apply forces while looping over a Set, a Map, or object keys, and the order is not identical on both machines, the result changes. Keep gameplay entities in an explicit array with a stable order you control.
  • Time and randomness. Date.now, Math.random, and the raw delta from requestAnimationFrame are all poison inside the simulation. Drive the sim off a fixed timestep and a seeded generator that both clients share, and keep wall-clock time out of gameplay entirely.
  • Anything that sneaks in async. A promise that resolves whenever, a bit of state touched by a loading callback, garbage collection nudging your timing. If it can happen at a different moment on the other machine, it does not belong in the deterministic core.

Do you even need rollback

Before any of that, ask whether your game needs rollback at all. Rollback earns its complexity in fast, input-heavy games where a few frames of delay wrecks the feel, so fighting games, platform fighters, tight action. A turn-based game does not need it. A card game does not. A slow co-op puzzle does not. For a lot of browser games the honest answer is an authoritative server with client-side prediction on movement, or even plain lockstep with a small input delay that players never notice because the game is not twitchy. I have shipped enough small games during game jams to trust the model I can actually finish and debug over the theoretically best one I abandon on Sunday night.

How I would actually approach it

If I were building a browser game that genuinely wants rollback, I would not open with the netcode. I would build it single player first, with a strict fixed timestep, a seeded random source, and every scrap of gameplay math routed through one place I own. Then, before touching a socket, I would write a determinism test: run the same input log twice and assert the final state hashes match. If they do not match on one machine, they will never match across two. That single test has caught more trouble for me than any amount of squinting at the network layer.

Only once the simulation is provably deterministic would I add the rollback layer on top: a ring buffer of past states, prediction for the remote input, and a rewind that re-simulates from the last confirmed frame. By then the netcode is almost boring, which is exactly the goal. The interesting failures are already dead because you spent your budget on the foundation instead of the buzzword.

The version of this I believe: rollback netcode is a solved pattern wearing a scary reputation, and the genuinely scary part lives one layer down in determinism. Get the game loop deterministic, prove it with a replay test, and the netcode falls into place. Skip that and you will spend your weekends bisecting desyncs instead of shipping. Keeping game state clean and predictable, which is most of what I argue for in structuring game state with an ECS, is what makes the whole thing tractable.
