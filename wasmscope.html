Wait — the browser can't step WebAssembly

That's right, and that's the whole point. WebAssembly.instantiate hands you a compiled function you can call, and nothing else. There is no API to pause it, read its operand stack, or ask what instruction it is on. DevTools can do it because it talks to the engine over a debugger protocol that pages don't get.

So this page doesn't ask the browser. It carries a second WebAssembly implementation, written from scratch in about a thousand lines of plain JavaScript: a binary decoder for the module format, a disassembler that prints the text format, and an interpreter with its own operand stack, locals, globals, table and linear memory. Because the stack is just a JavaScript array, it can be drawn on screen after every instruction.

How do you know the interpreter is right?

Because your browser is sitting right there as an oracle. Every time you hit Run, the same module is also instantiated with the real WebAssembly API, the same export is called with the same arguments, and the two answers are compared on screen. If they ever disagree, you'll see it.

Before shipping, the interpreter was differential-tested the same way against Node's engine: 128 numeric opcodes, roughly 28,700 argument combinations covering signed and unsigned comparison, division by zero, INT_MIN / -1 overflow, float rounding half-to-even, NaN propagation, saturating and trapping truncation, and 64-bit shifts and rotates. Plus recursion, loops with br_if, br_table out of nested blocks, call_indirect through a table, memory.grow, data segments and out-of-bounds traps. All of it matched.

What you can do with it

  • Look inside a .wasm you shipped and see how big each section really is, and which one is bloating your bundle.
  • Read the actual disassembly of a function instead of guessing what the compiler did with your Rust or C.
  • Step an algorithm and watch values enter and leave the stack — it is a very direct way to finally understand a stack machine.
  • Check what a third-party .wasm imports and exports before you trust it, without running it.

Limits, honestly

Decoding covers the MVP instruction set plus saturating truncation and bulk memory. Execution covers arithmetic, comparisons, conversions, locals, globals, all structured control flow, direct and indirect calls, and memory loads and stores. SIMD (v128) instructions are decoded but will stop execution rather than pretend. Imported functions are stubbed to return zero, so a module built for WASI or heavy JS glue will parse and disassemble perfectly but won't run end to end — the page says so when it happens. It is an interpreter, so it's thousands of times slower than the engine next to it; that's the trade for being able to see inside.

Is my file uploaded anywhere?

No. It's read with FileReader and parsed in JavaScript on your machine. No server, no API call. Load the page once and it works offline.

Why is my module's function called f12?

Most release builds strip the optional name custom section. When it's present, real function names are used; when it isn't, exports supply names and everything else falls back to its index. Building with debug info keeps the names.

It says imported functions were stubbed.

The module expects functions from its host (JavaScript glue, WASI, an environment import). This page has no host to supply them, so calls to them return zero instead of trapping. Disassembly is unaffected; execution results past that point aren't meaningful.

Can it handle a large file?

Parsing and disassembly handle multi-megabyte modules fine. Stepping is capped so a runaway loop can't hang the tab — Run stops after a large instruction budget and tells you.

Where can I get a .wasm to try?

There's one built into the page. Otherwise, any Rust, C, Zig, Go or AssemblyScript project targeting wasm32 emits one, and you can save any .wasm a site loads from your browser's network panel.
