Dynamic tool selection: why loading every tool wrecks your agent's accuracy

July 25, 20266 min readBy Harman Kamboj
AIAgentsTool callingMCP

Give an agent one tool and it uses it well. Give it eighty and it starts guessing. I ran into this the first time I wired a support agent to what felt like a sensible kit, maybe thirty tools spread across a couple of MCP servers, and watched it call the wrong one with total confidence. It did not fail loudly. It picked a plausible neighbour, borrowed half the arguments from a different tool's schema, and handed back something that read fine until I actually checked it. The fix was not a smarter model. It was dynamic tool selection: at each step, only show the agent the few tools that step could plausibly need.

I have been putting LLM features and small agents into real products for a while now, and this one surprised me because it runs against the obvious instinct. More capability should mean a more capable agent. With tools it goes the other way past a certain point, and the drop is steeper than you would expect.

The accuracy cliff nobody warns you about

A 2026 study that benchmarked this put numbers on what I had been feeling. Tool-calling accuracy sat around 78 percent with ten tools in the prompt and fell to roughly 14 percent once the catalog crossed a hundred. On a narrower slice, scheduling tasks, going from four tools to about fifty dragged accuracy down into the low single digits. Same model, same questions. The only thing that changed was how many tools it had to choose between.

That is not a gentle slope you can ignore until later. It is a cliff, and most teams walk off it without noticing because nothing throws an error. The agent keeps answering. It just answers wrong a little more often, and each wrong call is a whole round trip of latency and tokens spent on a mistake.

Why more tools make the model worse

When I looked at the bad calls, three things kept showing up, and none of them are mysterious once you see them.

  • Attention spreads thin. The model has to weigh every tool description against the request. Add forty near-identical descriptions and the signal for the right one gets buried under the noise of the almost-right ones.
  • Similar tools blur together. Two tools named search_orders and find_order with overlapping descriptions are a coin flip. The model does not know your naming history. It only has the text you gave it.
  • Arguments bleed across schemas. This was the sneaky one. The model would pick the correct tool and then fill a field with a parameter that belonged to a sibling tool, because both schemas were sitting in the same prompt and it stitched them together.

None of these are the model being dumb. They are what happens when you ask anything to discriminate between dozens of options that were written to sound alike.

This is the same disease as context bloat

If you have read my piece on how an MCP server eats the context window, this will feel familiar, because it is the same problem wearing a different hat. Every tool you register ships its full schema into the prompt on every call. That is permanent rent on your context, and it feeds the slow decay I wrote about in context rot. The tool selection failure and the context bloat failure are two symptoms of one habit: handing the model everything you have instead of the little it needs right now.

So the fix is the same shape too. Stop treating the tool list as a fixed manifest you set once at startup, and start treating it as something you assemble per step.

How I actually filter the toolset

The pattern that works for me is to keep the full catalog outside the prompt and retrieve into it. Embed the tool descriptions once, embed the user's request plus the current plan, and pull only the top handful of tools that match before each decision. The research world calls this tool retrieval or tool RAG, but the instinct is old. Return a tight slice, not the whole dataset. It is exactly the discipline I leaned on building the query layer behind ElasticSwap, where the difference between a fast product and a frozen one was refusing to hand back everything at once.

A few things I have learned doing this:

  • Retrieve on the evolving plan, not just the first message. What the agent needs at step five is not what it needed at step one, so I re-select as the task moves rather than picking a fixed set up front.
  • Pin a small core. A few tools get used constantly. Those I always include so retrieval never has to rediscover them, and I let the search fill the rest of the slots.
  • Group by phase when the work is stateful. If the agent is clearly in a read phase versus a write phase, I gate the write tools behind that state instead of paying to embed them every turn. This pairs well with the skip the tool server call for the boring, always-safe stuff.

The reported gains line up with what I have seen. That same benchmark moved from about 14 percent accuracy with the full catalog exposed to around 43 percent once it filtered the toolset by retrieval, and cut prompt tokens by more than half at the same time. Cheaper and sharper, from the same model.

Where retrieval bites back

I am not going to pretend this is free. The moment the right tool lives behind a retrieval step, a retrieval miss means the agent literally cannot see the tool it needs, and then it does something worse than pick wrong: it gives up or hallucinates a tool that does not exist. So the failure mode moves rather than vanishing, and you have to watch the new one.

What that changes in practice is where the care goes. Tool descriptions matter more now, not less, because the retriever reads them the same way the model used to. Your similarity threshold needs tuning against real traffic, since too tight drops the right tool and too loose brings the noise back. And you want to log the misses, the times the correct tool was not in the retrieved set, because that number tells you whether your descriptions and threshold are honest. I treat that like any other reliability metric, the same way I think about retries not corrupting real data.

The rule I follow now

Register few, expose fewer. When I am building an agent I still keep the full toolset available, but the prompt on any given step sees only what that step could use. The cheap test before you reach for a bigger model: count the tools in active rotation. If it is past fifteen or twenty and accuracy is soft, the model is not the problem, the menu is. Trim what it sees and the same model gets its judgement back.

Most agent failures I get called in to untangle are this, or its cousin the overstuffed context. Not a weak model, a model buried under options nobody curated. I keep more notes like this in my AI writing, and the rest of the work is on the homepage.
